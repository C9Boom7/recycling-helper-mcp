# Phase 12 — 동네 배출 장소 조회 툴 (`find_disposal_spots`)

## 목표

"상계동 사는데 폐의약품 어디 버려?"에 **실제 주소**로 답한다. 지금 지역 데이터는 "약국·보건소·주민센터 수거함"처럼
**어디 종류인지**까지만 말하는데, 기후에너지환경부 분리배출 API의 `getSpot`은 **어느 주소인지**를 준다.

이 서버의 첫 외부 런타임 의존이다. 그래서 이 PRD의 절반은 기능이 아니라 **실패했을 때 조용히 물러나는 방법**에 쓴다.
지금까지 서버는 외부 호출이 0건이었고([src/server.ts](../../src/server.ts)에 `fetch` 호출이 없다), 그 성질이 프리징
모델(9/14 이후 수정 불가)에서 자산이었다. 이 툴은 그 자산을 일부 내주고 들어온다.

### 왜 지금인가

[실측 문서](../moe-recycling-api-2026-08-24.md)의 원래 권고는 "본선 이후"였다. 뒤집는 근거는 셋이다.
1. 걸림돌 1순위였던 **배포 환경변수 주입이 가능하다고 저장소 주인이 확인했다**(2026-08-25). 원래 권고는 이게 미확인이라는 전제 위에 있었다.
2. 본선은 일반 사용자 투표다. "수거함 종류"와 "수거함 주소"의 체감 차이가 투표에 그대로 반영되는 종류의 기능이다.
3. 실패 설계(D2·D3)로 프리징 리스크를 "이 툴 하나가 폴백으로 내려앉는다"까지 좁힐 수 있다 — 기존 다섯 툴은 영향이 없다.

그래도 조건부다 — 아래 "일정과 게이트"의 손절 조건을 하나라도 못 넘으면 원래 권고(본선 이후)로 돌아간다.

## 배경 — API가 실제로 하는 것과 못 하는 것

실측은 [moe-recycling-api-2026-08-24.md](../moe-recycling-api-2026-08-24.md) 2장과, 이 PRD를 위해 2장에 덧붙인
"동별 종류 분포·지연 표본"(2026-08-25 추가분)이다. 이 문서의 숫자는 전부 그 두 곳에 있어야 한다.

| 항목 | 실측 |
| --- | --- |
| 입력 | `addr`(주소 부분일치) **또는** 좌표+반경. 함께 주면 둘 다 만족해야 해서 사실상 배타 |
| `addr` 제약 | **법정동만 통한다.** `상계동` 524건, `역삼동` 343건. 행정동(`상계1동`)·구(`강남구`)·시(`서울`)·역(`강남역`)은 전부 NODATA |
| 동음 오염 | 주소 문자열 부분일치라 `우동`은 화성 `석우동`에 걸리고, `서교동`은 마포 95건에 여수 9건이 섞인다 |
| 응답 | `spotNm`·`addrBase`·`addrDtl` 셋뿐. 좌표 없음, 종류 필드 없음, 종류 필터 파라미터 없음. `body.totalCount`는 온다 |
| 종류 | 절반 이상이 `종량제봉투 판매소`. 나머지가 폐의약품·폐건전지·형광등·의류·폐휴대폰·소형가전·투명페트병·음식물 RFID 등이고 표기가 지자체마다 제각각 |
| 성능 | `numOfRows=1000` 한 번에 270~540ms. 연속 12회 표본에서 11회 345~432ms, **1회 2,346ms**(2장 추가분) |
| 한도 | 개발계정 하루 10,000건 |
| 좌표 검색 | 되지만 쓰지 않는다 — 카카오 호스트가 사용자 좌표를 넘겨주지 않는다 |

이 제약이 설계를 결정한다: **법정동을 받아야 하고, 동음 오염을 우리가 걸러야 하고, 종류 정규화를 우리가 해야 하고,
느리거나 죽었을 때도 답이 비지 않아야 한다.**

## 방향 결정

### D1. 기존 툴 확장이 아니라 새 툴이다

`get_region_disposal_info`에 `dong` 인자를 붙이는 안을 배제한다.
- 기존 다섯 툴의 계약은 회귀 601건이 고정하고 있고, 마감 직전에 그 계약을 넓히면 실패가 다섯 툴로 번진다.
- 외부 의존을 새 툴 하나에 가두면, 본선 중 API가 죽어도 **죽는 것은 새 툴 하나**다.
- "어디에 버려?"(장소)와 "어떻게 버려?"(방법)는 다른 질문이라 description을 가르기 쉽다.

### D2. 실패해도 답이 비지 않는다

타임아웃·HTTP 오류·0건 — 어느 경우든 이 툴은 MCP 오류를 던지지 않고 **그 자체로 완결된 안내**로 내려앉는다(R5).
폴백은 특정 지역 객체에 기대지 않는다 — `region` 없이 `dong`만 온 기본 시나리오에서도 비면 안 된다.
MCP 오류로 끝나는 경우는 입력 검증 실패뿐이다.

### D3. 키가 없으면 툴 자체를 등록하지 않는다

`DATA_GO_KR_SERVICE_KEY`가 비어 있으면 `tools/list`에 이 툴이 아예 나오지 않는다. 등록해 놓고 매번 폴백으로
내려앉는 것보다 호스트가 처음부터 다른 툴을 고르는 쪽이 낫다. 로컬 스모크도 이 성질을 쓴다.
**구현 위치가 중요하다** — 등록·JSON-only 목록·디스패치가 전부 `TOOL_DEFS` 하나에서 나오므로([src/server.ts](../../src/server.ts)
209~214줄), 거르는 자리는 `TOOL_DEFS` **구성 단계** 한 곳이다. 갈래 하나만 걸러내면 "SSE 목록과 JSON-only 목록은
바이트 동일" 불변식(315줄 주석, 스모크가 대조)이 조용히 깨진다.

이 성질이 되돌리기 스위치를 겸한다: 키 env를 비우고 재배포하면 툴이 내려간다. 별도 플래그는 두지 않는다.
단, 콘솔 툴 목록 스냅샷(아래 "사람 개입 지점" 2번)이 낡은 툴을 계속 광고할 수 있다는 한계는 남는다 — 호출이 오면
unknown tool 오류가 아니라 호스트가 알아서 다른 툴로 넘어가는 것이 관측된 동작이지만, 보장은 아니다.

## 요구사항

### R1. 업스트림 클라이언트 (`src/moe-spot-client.ts`)

- `GET {BASE}/getSpot?serviceKey=…&pageNo=1&numOfRows=1000&addr={동}` **한 번**. 쪽 넘김 없음.
- `BASE`는 `MOE_API_BASE_URL`(기본 `https://apis.data.go.kr/1482000/WasteRecyclingService`)로 주입한다. 스모크가 로컬 목 서버를 꽂는 자리다.
- **타임아웃 2,500ms, 재시도 없음.** 1차 안은 1,500ms였으나 연속 12회 표본에서 1회가 2,346ms라, 1.5초면 정상 상태에서도 ~8%가 폴백으로 떨어진다. 가이드 예산이 p99 3,000ms(우리 평균 51ms)라 2.5초는 예산 안이다. 재시도는 최악 지연을 배로 만들므로 넣지 않는다.
- **키 취급 규칙 둘** — 실측 스크립트([probe-moe-recycling-api.mjs](../../scripts/probe-moe-recycling-api.mjs))가 이미 겪은 것을 그대로 옮긴다:
  - 디코딩 키는 `encodeURIComponent`로 인코딩하고, 인코딩 키(`%` 포함)는 그대로 쓴다. 이걸 틀리면 증상이 "툴은 등록됐는데 100% 폴백"이라 가장 늦게 발견된다.
  - 키는 로그·오류 메시지·응답 어디에도 싣지 않는다. URL을 로그에 남길 일이 있으면 `serviceKey`를 지운 형태로만.
- **응답 파싱 규칙 둘** — 같은 스크립트에서 옮긴다:
  - `items.item`이 단건이면 배열이 아니라 객체로 온다. 배열로 정규화한다(수거함이 한 곳뿐인 동에서만 터지는 버그의 자리다).
  - 게이트웨이 오류(키 오류·한도 초과)는 JSON이 아니라 XML로 온다. JSON 파싱 실패·비정상 resultCode·HTTP 오류·타임아웃을 전부 "실패" 하나로 접는다. 구분은 `_log`에만 남긴다(R6).
- `totalCount > 반환 행 수`면(1,000행 초과 절단) `_log`에 남기고 결과에 truncated 표시를 올린다 — R5가 "일부만 표시" 한 줄을 붙인다. 절단은 오류가 아니라 **특정 묶음이 통째로 빠진 완전해 보이는 답**으로 나타나는, 사용자가 눈치챌 수 없는 유일한 실패라서다. (실측 최대는 상계동 524행이라 지금은 닿지 않는다.)
- 하루 한도(10,000건) 관리는 하지 않는다. 닿으면 "실패"로 접혀 폴백이 나간다.

### R2. 입력 계약

```
find_disposal_spots(dong: string, region?: string, itemName?: string)
```

- `dong` — 필수. 법정동 이름(예: `상계동`). 행정동 표기는 규칙 하나로 정규화한다: `X숫자동` → `X동`(`상계1동`→`상계동`). 그 밖의 변형(`종로1가` 등)은 처리하지 않고 그대로 보낸다 — NODATA면 폴백이 받는다.
- `region` — 선택. 기존 툴과 같은 자유 문자열(`서울 노원구`). 있으면 `findRegionalPolicy`로 착지시켜 R4 필터에 쓴다.
- `itemName` — 선택. `resolveWasteItem`은 세 상태를 낸다 —
  - `match`: 그 품목이 걸리는 묶음만 내보낸다(R3의 `itemIds` 역인덱스).
  - `ambiguous` **또는** `not_found`: 품목 필터 없이 전 묶음 요약으로 떨어진다. 이 툴에서 품목명은 필터일 뿐이라 되묻지 않는다 — 장소 질문에 품목 되묻기로 답하면 원래 질문이 사라진다.

### R3. `spotNm` 정규화 묶음 (`src/data/spot-categories.json`)

구조는 `{ 묶음 id: { label, patterns[], itemIds[] } }`. **매핑은 이 표의 행 순서대로, 먼저 걸리는 묶음이 이긴다** —
`폐형광등∙폐건전지 전용 배출함`처럼 두 묶음 표기를 겸하는 실측 사례가 있어 순서가 계약이다.

| 순서 | 묶음 | patterns | 걸리는 품목 예 |
| --- | --- | --- | --- |
| 1 | medicine | `폐의약품` | 폐의약품 |
| 2 | battery_lamp | `전지 수거함`, `형광등` | 건전지, 형광등 |
| 3 | clothing | `의류` | 헌옷, 신발 |
| 4 | electronics | `폐휴대폰`, `소형가전`, `중소형 수거함` | 휴대폰, 소형가전 |
| 5 | pet_bottle | `페트병`, `무인회수기`, `자동수거기` | 페트병, 캔 |
| 6 | food | `음식물` | 음식물류 |
| 7 | trash_bag | `종량제봉투 판매소` | (품목 확정 시만) |
| 8 | etc | 나머지 전부 | (노출 안 함) |

- `itemIds`는 실제 품목 id를 적고 validate가 존재를 강제한다. 품목→묶음 역인덱스는 로드 시 계산한다.
- 새 표기는 `etc`로 떨어질 뿐 답이 틀리지 않는다. 프리징 전 마지막 재확인 때 대상 지역 동 몇 곳을 훑어 패턴 누락을 줄인다.

### R4. 동음 오염 필터 — 역추적 없이

`addr` 부분일치가 다른 시·도의 동을 섞어 온다(`서교동`에 여수 9건). 필터는 두 갈래뿐이다.

- **`region`이 있으면**: 착지 지역의 **광역 이름과 시·군·구 이름이 함께** `addrBase`에 있는 행만 남긴다. 광역 이름은 `metroId`가 가리키는 광역 지역의 이름·별칭에서 끌어온다. 구 이름 하나만 보면 안 된다 — 자치구 별칭에는 접두어 없는 `중구`류가 그대로 들어 있어 부산 중구 질의에 대구 중구 주소가 통과한다(전국 동명 자치구 문제. `prefixOnlyDistrictAliases`가 존재하는 이유와 같다).
- **`region`이 없으면**: 응답 행들의 시·군·구를 세어 **하나로 수렴할 때만** 내보내고(그 지역명을 응답 머리에 밝힌다), 둘 이상이면 "어느 지역의 {동}인지"를 묻는 되묻기로 답한다. 오염된 주소를 내보내는 것보다 되묻기가 낫다.

### R5. 응답 3갈래

**성공** (필터 뒤 묶음별 1건 이상):

```
## 서울 노원구 상계동 근처 배출 장소

### 폐의약품 수거함 (2곳)
- ○○약국 | 서울특별시 노원구 상계로 … 1층
### 폐건전지·형광등 (3곳)
- …

- 수거함 위치는 바뀔 수 있습니다. 방문 전 지자체 안내를 확인하세요.
- 출처: 기후에너지환경부 분리배출 정보조회 서비스
```

- 주소는 `addrBase`와 `addrDtl`을 공백 하나로 이어 붙이고 앞뒤 공백을 정리한다 — 실제로 수거함을 찾는 데 필요한 층·건물 설명이 `addrDtl`에 있다.
- **개수 상한: 묶음당 최대 3곳, 전체 최대 12곳. 전체 상한에 닿으면 R3 표 순서가 빠른 묶음부터 채우고 나머지 묶음을 자른다.** (`itemName` 없이 노출 묶음이 여섯이면 3×6=18이라 상한 둘이 충돌하는데, 순서 우선으로 정한다 — 의약품·전지처럼 "찾는 사람이 급한" 묶음을 위에 뒀다.)
- 절단 플래그(R1)가 켜져 있으면 "자료가 많아 일부만 표시했습니다" 한 줄을 덧붙인다.
- structuredContent: `{ found: true, dong, region?, categories: [{ id, label, spots: [{ name, address }] }], truncated?, source }`. 스모크 화이트리스트에 등록.

**폴백** (업스트림 실패·필터 뒤 0건): 지역 객체 없이도 완결되게, 세 요소로 짠다.

```
상계동의 배출 장소를 실시간으로 확인하지 못했습니다. 이렇게 확인할 수 있습니다.
- 생활폐기물 분리배출 누리집의 분리배출 장소 지도에서 동 이름으로 검색: https://www.xn--oy2b29bd3a601b.kr/…
- {region이 있으면: 그 지역의 공식 확인처·연락처 (formatRegionSourceList)}
- {itemName이 확정됐으면: 그 품목 묶음의 일반 안내 한 줄 — 예: 폐의약품은 약국·보건소·주민센터 수거함}
```

- 품목 묶음별 일반 안내 한 줄은 `spot-categories.json`에 `fallbackLine` 필드로 넣는다 — 폐의약품·전지는 기존 `regionSpecialCollectionLines`가 다루지만 의류·페트병·소형가전은 다루지 않으므로, 지역 함수에 기대지 않고 묶음표가 제 폴백 문장을 들고 있는다.
- structuredContent: `{ found: false, dong, fallback: { mapUrl, regionSources?, itemLine? } }`. **업스트림 오류 내용은 싣지 않는다.**

**되묻기** (R4 미수렴): 무엇을 다시 달라는지 한 줄 — "여러 지역에 같은 이름의 동이 있습니다. 시·군·구를 함께 알려주세요(예: 서울 노원구 상계동)." structuredContent `{ found: false, ambiguousDong: true, regions: [...] }`.

### R6. 로깅·운영·description

- `_log`: `status: "spots" | "spots_fallback" | "spots_ask"` + `upstream: "ok" | "timeout" | "http" | "empty" | "truncated"` + `upstreamMs`. 동 이름 등 인자는 `CALL_LOG_DETAILS` 규칙대로 기본 미기록.
- 환경변수: `DATA_GO_KR_SERVICE_KEY`(비밀 — 커밋 금지), `MOE_API_BASE_URL`(테스트용). 별도 켬/끔 플래그 없음(D3).
- description: 한 문장 요약 + 트리거 예("폐의약품 수거함 어디", "폐건전지 버리는 곳", "헌옷수거함 위치") + **동 이름(법정동)이 필요함**을 명시 + "버리는 방법을 물으면 `get_disposal_steps`" 대비 문구. phase-0의 길이·형식 제약을 따른다.

### R7. 검증

- 스모크에 로컬 목 업스트림을 띄우고(`MOE_API_BASE_URL` 주입, 픽스처는 상계동 실측 응답 축약본) 여섯 갈래를 고정한다:
  ① 성공 응답 모양·개수 상한 ② 타임아웃 폴백(목이 3초 지연) ③ 0건 폴백 ④ 동음 되묻기(두 시·군·구 섞인 픽스처) ⑤ 단건 `items.item` 객체 정규화 ⑥ 키 없는 실행에서 `tools/list` 5개 유지.
- **스모크 spawn env에서 `DATA_GO_KR_SERVICE_KEY`를 명시적으로 고정한다** — 목 실행에는 더미 키, 기본 실행에는 빈 값. 개발자 셸에 키가 export돼 있으면(실측 관행이 그렇다) 상속만으로 툴이 6개가 되어 목록 완전일치 단언부터 깨진다. `WIDGET_ENABLED`를 고정해 둔 것과 같은 이유고, 그 주석 바로 옆에 둔다.
- 응답 크기 상한은 이 툴의 측정값 + 10% 여유로 새로 정하고(다른 툴 기준을 빌리지 않는다), 기존 관행대로 경고로 시작한다. 목표는 성공 응답 text 2.5KB 이하 — 12곳 상한이면 닿는 값이다.
- `pnpm local:test` 전체 통과. **실서버를 치는 케이스는 CI에 넣지 않는다.** 기존 다섯 툴 케이스 601건은 무변경.
- 배포 후 Preview 실발화 2건("상계동 폐의약품 수거함 어디야", "역삼동에서 헌옷수거함 어디 있어") — 판정은 "Kakao Tools 확인 중" 실시간 지표.
